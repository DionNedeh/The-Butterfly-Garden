| Scenario | fps | p95 frame | Frames > 33 ms | Main-thread busy | Layouts |
| --- | ---: | ---: | ---: | ---: | ---: |
| Garden, normal CPU | 54 | 33 ms | 8 | 1.75 s of 4 s | 218 |
| Garden, 4× slower CPU | **22** | **83 ms** | **53** | 3.89 s of 4 s | 89 |
| Same, with the SVG-internal CSS animations switched off, 4× CPU | **53** | 33 ms | 10 | 1.00 s | **0** |

The A/B rows isolate the cause. Wing flaps, plant sway, aura spins and the
egg/caterpillar/chrysalis wobble are CSS keyframes on elements *inside* an
inline `<svg>`. Chromium cannot hand those to the compositor, so it
recalculates style and re-lays-out the SVG on every frame. That is about 86 %
of the garden's main-thread work. The butterflies' flight paths already use
compositor-friendly Web Animations on HTML wrappers, and those cost almost
nothing.

With three years of daily use (1,095 moods and reflections, 5,475 Sunlight
awards and completions) at 4× CPU, a cold reload reaches the app shell in
1.33 s. Re-opening Today takes 240–275 ms, and saving a mood costs about 11 ms
over the idle baseline. **Data volume is not a bottleneck today; animation is.**

Caveat: this is headless Chromium in a shared container. The relative
differences are solid; the absolute numbers are not a real phone.

**Reproductions.** The three most serious data findings (D1, D2, D6 below) were
each reproduced with a throwaway Vitest file against `fake-indexeddb`. The file
was then deleted and nothing was committed. Each is marked *Reproduced*. A
finding confirmed by following the code path end to end is marked *Traced*.

### a.3 What "zero loss" means for every change below

1. **No capability is removed.** Every screen, setting, collectible and flow
   keeps working the way a gardener knows it.
2. **No stored garden becomes unreadable.** Changes to `AppState` are additive.
   `CURRENT_STATE_VERSION` is only raised with a migration and a "loads a
   garden from before" test.
3. **The backup envelope stays readable both ways.** Old backups import
   into the new build. New fields are optional, so older builds that ignore
   unknown keys still import new backups.
4. **The invariants in `docs/handoff-p5-store-split.md` §3 stay pinned.**
   Never overwrite an unreadable garden; deletion fails loudly; a failed
   write is surfaced once; no write-back of a garden just loaded; a garden with
   a missing collection is withheld. Write-through saves stay. **No debounce.**
5. **Each fix starts as a failing test.** The fix lands only with that test
   turning green, and the four repository checks (`typecheck`, `lint`, `test`,
   `test:e2e`) pass.

### a.5 The plan

Seven work packages, in the order they should land. Each lists its steps, what
keeps it zero-loss, and how to know it is done.

#### WP1 — A safety net before any surgery

*Fixes the conditions for D1, D2, D4–D7 and T1.*

1. Turn the repository from a module singleton into a factory,
   `createGardenRepository(dbName = 'butterfly-garden')`. Keep the exported
   `gardenRepository` as the default instance, so no caller changes. Tests can
   then hold **two instances on one database**, which is a faithful model of two
   tabs.
2. Write the failing tests first:
   - a newer tab's write followed by an edit here leaves the newer data in place (D1);
   - a damaged backup is refused with a readable reason (D2);
   - an unreadable garden never shows Onboarding (D4);
   - exporting a withheld garden never produces an empty file (D5);
   - quarantine stays at one copy per distinct record (D6);
   - delete with another instance open never leaves a partial garden (D7).
3. Add a root `<ErrorBoundary>` in `main.tsx` that renders a calm **safe mode**.
   It explains what happened, offers *Download what's stored* (it reads the raw
   records straight from IndexedDB, bypassing React state) and *Restore a backup*,
   and only then, behind confirmation, *Start fresh*. Add per-view boundaries, so a
   broken Journal entry cannot take the Garden down with it.

*Zero-loss guard:* nothing user-visible changes except that a crash now lands
somewhere useful.
*Done when:* the new tests fail on `main` and the boundary renders on an
injected throw in every view.

#### WP2 — Make data loss structurally impossible

*Fixes D1–D13.*

1. **Adopt outcomes (D1).** In the hook, treat every `adopt()` result
   explicitly: `loaded` → apply; `withheld` → go read-only through the same
   path as a launch-time withhold; `unavailable` → retry a full load with
   backoff, staying read-only until it succeeds. In the repository, never clear
   the baseline on an adopt fallback unless the caller takes the result.
   Defence in depth: add a monotonically increasing `revision` to `meta`, written
   in the same transaction as every save. A save whose base revision is older
   than what is stored aborts and reloads instead of writing. This is optimistic
   concurrency at no extra cost, since `meta` is already in almost every
   transaction.
2. **Deep validation (D2, D11).** Give each collection an element validator.
   Validators are pure functions, so there is no new dependency.
   - **Repair or drop** what can be re-earned (Sunlight rows, inventory counts,
     outfit ids, `theme`) and report a count of what was dropped.
   - **Refuse** anything that would silently lose writing (moods, reflections,
     recaps, goals with text). The importer already does exactly this for
     images.
   - Use the same validators on load and on import, so a stored garden and a
     backup are held to one standard.
3. **Ask the browser to keep the garden (D3).** Call `navigator.storage.persist()`
   after onboarding and again after the first journal entry. Show in Settings
   whether storage is *protected* or *best-effort*, plus `estimate()` usage. On
   Safari, say plainly that adding the app to the Home Screen is what protects
   the journal from Safari's seven-day clean-up.
4. **Recovery screen (D4, D5, D6).** When the garden is withheld and there is no
   profile, show a recovery screen instead of Onboarding. It names the reason
   and offers:
   - *Try again* (for `unavailable`);
   - *Download the set-aside copy*, from `quarantined()`;
   - *Restore a backup*;
   - *Start a new garden*, which keeps the set-aside copy.

   While read-only, the export button downloads the quarantined raw record,
   clearly labelled, and never the blank display state. Store one quarantine
   record per distinct content, keyed by a SHA-256 hash, capped to the newest
   three, with *Discard set-aside copies* in Settings.
5. **Coordinated delete (D7).** Before deleting, broadcast `garden-clearing` and

   blocked, change the copy to "Deletion will finish when the other tabs close",
   because that is what the spec does.
6. **Undoable restore (D8).** Before `replace()`, write the current garden into a
   `snapshots` store, keeping the last two. Show a preview of the file first:
   export date, app version, counts per collection, and the date range of the

   Settings. Cap backup reads at 64 MB before `file.text()`.

## (b) Strengthening Existing Features

This section takes what the PWA already does and makes each part kinder,
clearer or deeper. Nothing here is a new pillar; those are in (c). Each idea
names the code it touches, why it helps (evidence or what I saw using the app
on a phone-sized screen), and a rough size: **S** ≤ 1 day, **M** 2–5 days,
**L** > 1 week.

### b.1 Principles every change follows

These come out of the research. Each one is something the app already mostly
does, made explicit so the new work keeps doing it.

1. **Never punish a gap.** Broken streaks make people quit, especially when they
   blame themselves, and missing a day does not hurt habit formation
   ([Silverman & Barasch 2023](https://www.colorado.edu/business/news/2023/04/20/research-streaks-marketing-tech-barasch);
   [Lally et al. 2010](https://bps.org.uk/research-digest/how-form-habit)).
   The onboarding promise "Nothing here wilts when you need time away" is
   already right. The streak is the one place the app breaks it.
2. **Reward the act, never the value.** Sunlight for a check-in must never depend
   on the weather chosen, and nothing should nudge the choice. Defaults steer
   choices strongly (d = 0.68 across 58 studies,
   [Jachimowicz et al. 2019](https://ideas.repec.org/a/cup/bpubpo/v3y2019i02p159-186_00.html)).
3. **Counting can make care feel like work.** Measurement raises output but
   lowers enjoyment ([Etkin 2016](https://www.fuqua.duke.edu/duke-fuqua-insights/etkin-counting-steps)).
   So numbers should be easy to hide, and feedback should describe rather than
   score.
4. **Wellbeing is never paywalled.** The Pass stays cosmetic and scenic. This
   matches how the best-reviewed apps in the category are monetised (Kinder
   World, Focus Friend) and avoids the complaints that heavier paywalls attract
   (Reflectly, Flutter).
5. **No clinical claims, no scores.** Insights stay simple and verifiable:
   counts and calendars, no screening questionnaires, no "risk" signals. That
   keeps the app a wellbeing product under UK MHRA guidance (low functionality,
   no disease purpose) and Google Play's health policy
   ([MHRA 2026](https://www.gov.uk/government/publications/digital-mental-health-technology-qualification-and-classification),
   [Play](https://support.google.com/googleplay/android-developer/answer/16679511)).
6. **Privacy is part of the product.** No feature adds a network request of its
   own. Where something leaves the device (a shared image, a backup), it is
   because the gardener tapped a button that says so.

## (c) Major New Capabilities

These are new things the garden could do, chosen to fit what the app already
is: private, offline, gentle, and about real butterflies. Each one keeps the
promise that the app's own code makes no network request. Where data could leave
the device, it is because the gardener explicitly hands it to something else:
the system share sheet, a calendar or a file.

For each capability: what it is, why it belongs here, how it feels to use, how
it would be built in this codebase, and what could go wrong. Sizes are rough:
**M** about a week, **L** two to four weeks, **XL** more, mostly content or art.

### c.1 Breathe with the butterfly

**What.** A one-to-five-minute guided breathing exercise in which a butterfly's
wings are the pacer: they open as you breathe in and close as you breathe out.
The default is slow, exhale-longer breathing (about 4 seconds in, 6 out, both
adjustable). An optional "cyclic sigh" pattern is offered. There are no breath
holds or fast patterns.

**Why.** Slow breathing has some of the better evidence of anything a self-care
app can offer. A 2023 meta-analysis of 12 RCTs found small-to-moderate drops in
stress (g = −0.35), anxiety and depression scores
([Fincham et al. 2023](https://doi.org/10.1038/s41598-022-27247-y)). In a remote
RCT, five minutes a day of exhale-focused cyclic sighing improved mood more than
mindfulness meditation ([Balban et al. 2023](https://doi.org/10.1016/j.xcrm.2022.100895)).
Stand-alone breathing apps keep almost nobody past 30 days
([Baumel et al. 2019](https://pmc.ncbi.nlm.nih.gov/articles/PMC6785720/)), so
this lives *inside* existing moments rather than as a separate destination.

**Experience.**
- It is offered where it helps: the "Take three slow breaths" suggested goal,
  after a heavy-weather check-in (b.2 T3), as a Moonlight step, and on the
  support page.
- The gardener picks their active companion, or Marigold, as the pacer, and sees
  "In… 4 · Out… 6". A soft tone from the existing Web Audio engine can mark each
  turn; with eyes closed or reduced motion, the count and tone carry it instead
  of the wings.
- *Stop* is always one tap. Copy: "If you feel light-headed, breathe normally."
- Finishing counts as an act of care, once a day.

**Build.**
- `src/components/BreathingSession.tsx`. A `useBreathPacer(pattern)` hook drives
  a single Web Animations timeline on the composited wing layers from a.5 WP4.
- The tone is a new voice in `useAmbientSound.ts`.
- `BreathPattern` data in `src/data/breathing.ts`.
- A session is recorded as a `SunlightAward` with source `breath:<date>`. No new
  collection is needed.

**Risks.** No claims beyond "a calming exercise". Never suggest it treats
panic. Default to the gentlest pattern.

**Size:** M.

### c.2 Noticed in Nature

**What.** A real-world companion to the in-app garden. Once a day, an optional
prompt asks: *"What did you notice in nature today?"* There is also a field
book in which the gardener logs **real sightings**: a butterfly or plant from
the field guide, a date, a few words and an optional photo. Real sightings earn
a pressed-flower stamp on that species' field-note card.

**Why.** This is the single most on-theme idea with strong evidence behind it. In an
RCT of 582 people, an app that prompted them to notice good things about urban
nature produced sustained wellbeing gains. For participants with a common
mental-health difficulty the improvement was clinically significant
([McEwan et al. 2019](https://doi.org/10.3390/ijerph16183373)). No competitor
ties self-care to noticing real butterflies. Flutter, the closest themed game,
is a pure game with ads.

**Experience.**
- "Three good things in nature" as a reflection family (b.2 T9).
- *Log a sighting* from the Journal or the Guide: pick a species or plant (searchable,
  regional list per b.8 F2), add a note and optionally a photo, and save.
- The field-note card shows "Seen in the wild on {date}" next to "Welcomed in
  your garden".
- A gentle, seasonal "what to look for" line ("Monarchs are on the move south
  this month").
- An optional, clearly marked outbound link to a citizen-science programme
  (iNaturalist, Big Butterfly Count) that opens in the browser, never from the app.

**Build.**
- A new `sightings` collection, added through the six-step checklist in
  `gardenRepository.ts`: a new store, `DATABASE_VERSION` + 1,
  `CURRENT_STATE_VERSION` + 1, `COLLECTION_SINCE_VERSION.sightings`, defaulted
  in `migrateState`, and included in backups.
- Photos reuse the custom-backdrop pipeline (`prepareBackdrop`: header sniffing,
  megapixel cap, re-encode to strip location metadata) at a smaller maximum edge,
  stored as Blobs (a.5 WP5-2).
- No location is read, ever.

**Risks.**
- Photos grow backups; cap at around 50 photos, with clear storage use shown in
  Settings.
- Never encourage catching or handling.
- Species facts need the accuracy pass in b.8 F1.

**Size:** L.

### c.3 Raise it with a goal

**What.** When a new egg appears, the gardener can *adopt* it to one of their own
goals ("Drink water", "Walk outside"). Completing that goal counts as a care day
for that companion, alongside the care menu. When it emerges, the butterfly
carries the goal's name in its story: "Grown alongside *Walk outside* · 9 days".

**Why.** It joins the two halves of the app. Today, self-care (Today) and
companion care (Care) are parallel tracks linked only by currency. Finch's
"micropets" pattern shows the appeal of tying a creature to a habit.
Behavioural activation — small, valued, scheduled activities — is among the
best-supported self-help approaches
([Cochrane 2020](https://doi.org/10.1002/14651858.CD013305.pub2)). The days
need not be consecutive, so it inherits the app's no-punishment rule.

**Build.**
- Optional `CreatureInstance.adoptedGoalId`.
- In `completeGoal`, also call a pure `careFromGoal(state, goalId, date)` in
  `lib/lifecycle.ts` that marks a care day for an adopting creature (idempotent per
  day).
- Care actions remain, and either path counts.
- Archiving or deleting the goal releases the companion back to normal care,
  with no loss.

**Risks.** A creature must never "wait" visibly on a missed goal. Copy stays
about what was done, not what wasn't.

**Size:** M.

### c.4 A garden letter, and your garden's year

**What.** Two private keepsakes, made on the device:
- **A weekly garden letter from Marigold.** A short, descriptive note each Sunday
  evening: "This week you checked in four times, finished eleven goals and closed
  three evenings. You wrote: '*the light on the river after work*'." It quotes
  one of the gardener's own lines (one they starred, or the longest) and the
  week's new arrivals. It contains no analysis, scores or advice.
- **Your garden's year.** At the turn of the year, or any time on request, a
  scrollable recap: the weather calendar, species welcomed, favourite prompt
  answers, longest rhythm. It ends in a **postcard image** (the garden scene with
  your butterflies) that can be saved or shared through the system share sheet,
  only if the gardener taps *Share*.

**Why.** Reviewing your own data is what brings people back after a lapse
([Epstein et al. 2015/16](https://library.selfresearch.org/research/a-lived-informatics-model-of-personal-informatics/)).
Descriptive, verifiable summaries keep it on the wellbeing side of MHRA's
classification. A shareable image is the one form of "social" that needs no
server.

**Build.**
- `lib/summaries.ts`: pure functions over `AppState` returning counts and chosen
  quotes. A `letters` collection is unnecessary: letters are computed on demand.
  Only "letter read" is stored, in `meta`.
- The postcard is drawn to an `OffscreenCanvas` from the sprite SVGs and the
  current backdrop, then handed to `navigator.share({ files })`, with a download
  fallback.
- An optional *star this line* on journal entries feeds the quotes
  (`ReflectionEntry.starred?`).

**Risks.**
- Quoting a painful entry back can hurt. Quote only starred lines, or none, by
  the gardener's choice in Settings.
- Never compare weeks ("less than last week").

**Size:** M (letter) + M (year).

### c.5 Private by design: lock and encrypt

**What.** An optional **garden lock** for the PWA. With it on, the journal is
**encrypted at rest** in IndexedDB, and the app opens to a calm lock screen
until the passcode, or on supporting devices a passkey, is given. **Encrypted
backups** are a separate, independent option: *Download a protected backup*
asks for a passphrase and writes a file only that passphrase can open.

**Why.**
- A mood journal is sensitive, and app lock is a standard expectation in the
  category (Daylio, Day One, Finch).
- On a shared computer or family tablet, "it never leaves the device" is not
  the same as "only I can read it".
- The plain JSON backup is the app's most exposed copy: it sits in Downloads or a
  cloud folder.

**Experience.**
- Settings → Privacy → *Lock my garden*: choose a passcode, then **save the
  recovery key**. That is a printable or downloadable sheet with a 24-word code,
  and the gardener confirms two words from it before the lock turns on.
- Where WebAuthn's PRF extension is available (Chrome on Android with Google
  Password Manager passkeys, Safari with Touch ID or Face ID), *Unlock with a
  passkey* is offered as a faster second path. It falls back to the passcode
  everywhere else ([Corbado](https://www.corbado.com/blog/passkeys-prf-webauthn),
  [WebKit bug 311099](https://bugs.webkit.org/show_bug.cgi?id=311099)).
- An auto-lock after N minutes hidden is optional.

**Build.**
- **Key hierarchy.** A random 256-bit data key encrypts the garden. That key is
  wrapped separately by: a passcode-derived key (Argon2id at OWASP's minimum of
  19 MiB, t = 2, via a small WebAssembly module; or PBKDF2-HMAC-SHA-256 at
  ≥ 600,000 iterations if WASM is unavailable
  ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)));
  the recovery-key-derived key; and optionally the passkey PRF output. Changing
  the passcode re-wraps the data key without re-encrypting the garden.
- **Where encryption happens.** Inside `gardenRepository`, at the part boundary:
  each part's value is serialised and sealed with AES-GCM (a fresh 96-bit IV, part
  name as additional data) before `put`, and opened after `get`. Everything above
  the repository is unchanged, as the handoff doc's "storage details do not leak
  upward" rule requires.
- **Protected backups.** A new envelope (`format: 'the-butterfly-garden-sealed'`,
  KDF parameters, salt, IV, ciphertext). The existing plain envelope keeps
  working unchanged.
- **Cost.** An encrypted write of a three-year `sunlight` part (~550 KB) is a few
  milliseconds of AES-GCM on a phone. The measured 11 ms save stays comfortably
  interactive.

**Risks.**
- **A forgotten passcode with a lost recovery key is permanent loss.** The flow
  must say so plainly, twice. It must also let the gardener *turn the lock off*
  (decrypting in place) at any time while unlocked.
- **The lock does not protect against code running on the same origin.** That is
  one more reason for a.5 WP3's own-origin move.
- **Ship this only after WP1 and WP2.** The repository must be rock solid before
  it holds ciphertext.

**Size:** L.

### c.6 Move and keep: transfer and automatic backups

**What.** Three ways to make the "only copy is on this device" problem smaller,
none of them needing a server:

1. **Move to a new device.** On the old device, *Move my garden* creates a
   protected backup (c.5) and shares it through any channel the gardener likes:
   AirDrop, Messages, email, a cloud drive. It then shows a **QR code holding the
   one-time decryption key**. On the new device, *Arrive from another device* asks
   for the file and scans the QR. The file can travel through untrusted channels,
   because the key never travels with it.
2. **Automatic backups on desktop.** On Chromium desktop browsers, *Keep a backup
   file up to date* lets the gardener pick a file once. Chrome 122+ can remember
   the permission ("Allow on every visit",
   [Chrome](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api)),
   and the app rewrites that file after each day's changes.
3. **Rolling snapshots everywhere.** The `snapshots` store from a.5 WP2-6 keeps the
   last seven daily snapshots locally, so a mistaken delete or restore can be
   undone. This protects against mistakes, not eviction; the copy says so.

**Build.**
- The QR key encoding uses a tiny encoder. Scanning uses `BarcodeDetector` where
  available (Chrome on Android), with a small pure-JS decoder fallback for iOS
  Safari, which still ships it disabled
  ([caniuse](https://caniuse.com/mdn-api_barcodedetector)). Typing a 12-word code
  works everywhere.
- The file handle is stored in IndexedDB. The write runs from the save effect,
  throttled to once a day plus "on close" via `visibilitychange`.
- Everything is feature-detected; nothing degrades for browsers without it.

**Size:** L.

### c.7 Seasons in the garden

**What.**
- **The garden follows the real calendar, gently.** Spring brings emerging
  swallowtails and early nectar plants; high summer, full blooms; autumn, the
  monarch migration (Marigold, a monarch, prepares to travel and returns in
  spring); winter, overwintering chrysalises and mourning cloaks basking on mild
  days.
- **Seasonal observation lines and prompts.**
- **A free seasonal keepsake each season.** Pass holders also get a seasonal
  outfit.
- **A hemisphere switch.** Seasons follow the gardener's region from b.8 F2, so
  Australian winter is not shown in July snow.

**Why.** It keeps a long-running garden fresh without new mechanics, the way Finch
and Pokémon Sleep run events, but offline. It teaches real phenology, which
deepens the "real butterflies" identity. It also gives the Pass something to grow
into without paywalling wellbeing.

**Build.**
- `src/data/seasons.ts`: date windows per hemisphere, scene overlays (petals →
  falling leaves → frost), observation lines, the keepsake item.
- A pure `currentSeason(date, hemisphere)` in `lib/seasons.ts`.
- Content ships with releases; there is no server.
- Marigold's autumn departure is cosmetic: she never actually leaves the guide role.

**Risks.**
- Accuracy: phenology varies by latitude, so wording stays broad ("in much of
  North America…").
- **Art cost is the real cost.**

**Size:** L per year of content, mostly art.

### c.8 A comfort plan

**What.** A private page the gardener writes for their harder days. It holds what
helps, people they can reach (name and number, tap to call), places that feel
safe, kind words to themselves, and reasons that matter. It links from the
support page (b.10 P10) and from gentle-day mode.

**Why.** Safety-planning-type interventions reduce suicidal behaviour in clinical
trials ([Nuij et al. 2021](https://doi.org/10.1192/bjp.2021.50)). A self-written
comfort plan is the non-clinical, self-care version of that idea.

**Build.**
- A small `comfortPlan` record in `meta`. It is in backups and, when locked,
  encrypted like everything else.
- Original wording only: the well-known Stanley–Brown template is copyrighted.
- No risk detection, no keyword scanning of the journal, no prompts to fill it in
  after a bad check-in.

**Risks.** It must never be framed as a clinical safety plan or a substitute for
help.

**Size:** M.

### c.9 Reminders without a server

**What.** The PWA cannot schedule notifications without a push server, and iOS web
push also needs one. Rather than add one, the app offers **calendar reminders**.
*Add a daily garden visit to my calendar* downloads a small `.ics` file: a
recurring event at the gardener's chosen time (morning check-in, or evening
Moonlight), with a link back to the app. The gardener's own calendar does the
reminding. The event text is neutral ("Garden time 🦋") and holds nothing from the
journal.

**Why.** Reminders bring a small engagement lift
([Bidargaddi et al. 2018](https://doi.org/10.2196/10123)), and some people need
them for memory support. In the category, reminders are one of the most
requested features and pushy ones one of the most hated. A calendar entry is
opt-in, user-owned, and trivially removed.

**Build.**
- A `.ics` with `RRULE:FREQ=DAILY` and a `VALARM`, in floating local time so it
  follows the gardener across time zones.
- iOS Safari handles calendar files most reliably from a direct `.ics` URL served
  as `text/calendar`
  ([Apple forums](https://developer.apple.com/forums/thread/101947)). So ship a
  handful of static files for common times (`/reminders/morning-0800.ics`,
  `/reminders/evening-2030.ics`…) and generate custom times as a Blob download.
- **Test on real devices before announcing.**

**Size:** S–M.

### c.10 The garden in other languages

**What.** Spanish, French, German and Brazilian Portuguese first, then more by demand.

**Why.** The app is English-only. A calm, private, free-at-heart self-care app is
exactly what translates well.

**Build.**
- Move user-facing copy into message catalogues. The catalogue-as-data style in
  `src/data/*` already makes this tractable.
- Use ICU message format for plurals (fixing "1 days" for free).
- Language comes from `navigator.language` with a Settings override.
- Dates already go through `Intl`.
- Species and plant common names need per-locale names; scientific names stay.
- Lazy-load locale catalogues as separate chunks, so the English bundle does not
  grow.

**Risks.**
- Wellbeing copy needs a native-speaker review, not machine translation alone.
- The support page needs per-country verified services.

**Size:** XL (mostly content).

### c.11 Considered and not recommended

| Idea | Why not |
| --- | --- |
| An AI journaling companion | It would send the journal off-device or ship a large local model. Trust in AI for mental health is low, the APA's 2025 advisory urges caution, and summarising or advising on entries moves the app towards MHRA's "medical purpose". The app's strongest differentiator is that no one, human or machine, reads the journal. |
| Mood insights with statistics ("your mood drops on Mondays") | Small-sample "findings" mislead. MHRA counts diary graphs with statistical flags as higher functionality. Descriptive calendars (b.4 J3) give most of the value with none of the risk. |
| Friends, sharing feeds, cloud sync accounts | Each needs a server and an identity. That breaks the no-account promise and adds a data controller. The postcard (c.4) and device move (c.6) cover the real needs. |
| Web push notifications | They need a push server and VAPID keys, and on iOS only work for Home Screen apps. Calendar reminders (c.9) are private and opt-in. |
| Screening questionnaires (PHQ-9, GAD-7) | These are clinical instruments. They would make the app a medical device under MHRA and FDA guidance. |
| Selling currency or "streak repair" | Exploitative by the streak research's own account, and within the EU Digital Fairness Act consultation's scope (virtual currencies, penalties for disengagement). Currencies stay earn-only. |

## Implementation log

The plan is being carried out one section at a time, each merged only once it
passes typecheck, lint, the unit suite, the Playwright suite (desktop, phone
and the Android bundle) and the Gradle Android checks. Owner decisions taken

### PR A1 — data safety (a.5 WP1 and WP2)

- **Repository as a factory** (`createGardenRepository`), so tests hold two
  instances on one database, which models two tabs. The default
  `gardenRepository` is unchanged for callers.
- **D1** Every save carries a revision stored in `meta`. A save made against an
  older revision is refused (`GardenConflictError`) and the tab reloads
  instead of overwriting. Saves from one tab are queued, never raced. The hook
  now handles every `adopt` outcome: anything but `loaded` pauses saving and
  keeps the garden on screen. The repository also refuses to save while its
  last read was withheld.
- **D2 / D11** `validateGarden` checks every entry. Re-earnable data is
  repaired or dropped and counted. Writing that cannot be placed refuses the
  garden rather than being dropped. Text of the wrong type stays as text. A
  root error boundary opens **safe mode** (download everything stored, restore
  a backup, then start again), and every page has its own boundary.
- **D3** `navigator.storage.persist()` is requested after onboarding, after
  the first journal entry and on each launch with a garden. Settings shows
  whether storage is protected and how much is used, with Safari Home Screen
  guidance.
- **D4–D6** An unreadable garden opens a **recovery screen**, never onboarding.
  Export is refused while read-only, and the set-aside copy is offered
  instead. Quarantine is keyed by a SHA-256 fingerprint, so a garden is set
  aside once, capped at three copies, with download and discard in Settings.
- **D7** A delete warns other tabs first (`garden-clearing`), then tells them
  it's done (`garden-cleared`). A tab whose connection saw the delete can
  never write the garden back. A delete blocked by another tab is reported as
  pending, which is what IndexedDB actually does.
- **D8** A restore shows what the file holds (garden name, counts, date range,
  export date and version, repairs) before replacing anything. It snapshots
  the garden it replaces (two kept) and offers **Undo the restore**. Backup
  files over 64 MB are refused before they are read.
- **D9 / D10 / D13** Image saves settle exactly once, with a 30 s ceiling. A
  dropped connection is forgotten so the next save reopens it. A newer
  database reads as "update the app". Migrations, version catch-up and restore
  use strict durability.
- **D12** Unsaved mood notes, reflections and recap answers are kept as
  drafts in their own store (never exported, never rewarded). A recap opened
  before 04:00 stays open for its day.
- Found while doing this: the persistence banners and Settings notes had no
  styles at all. They are now styled in both themes.
- Tests: 41 new unit and component tests (two-tab repository, validator, hook
  paths, safe mode, recovery, restore preview, drafts) and a new e2e test of
  the recovery screen in a real browser. 440 unit and 48 e2e tests pass.

### PR A2 — hosting, the compositor and tidy-ups (a.5 WP3, WP4 and WP5)

**WP4 — the garden on the compositor**

- **P1** Sprites are now a frame of stacked `<svg>` layers (`SpriteFrame`), and
  each moving part (both wings, the plant sway, the egg, caterpillar and
  chrysalis, each aura) is its own layer. The CSS animates the layer, not an
  element inside an SVG.
  - Measured on the 12-butterfly garden at 4× CPU, after a warm-up:
    - 28.8 → 51.2 fps (range 45–57);
    - per-frame layouts gone (from ~30 a second to 0);
    - main-thread time per 5 s down from 4.9 s to 2.3 s;
    - an idle garden's main thread busy 0.93 s in 4 s instead of 1.96 s.
  - The layer tree confirms every sprite animation now has its own compositor
    layer. Before, the `<use>`-based wings and the auras did not.
  - Sprites out of view pause, through one shared IntersectionObserver, and a
    hidden tab pauses every sprite, not just the wings.
- **Calm motion**: a third setting between Full and Reduce. Wings, plants and
  auras move at about half speed. Flight paths keep 70% of their reach, take
  60% longer and bank half as steeply. Only four butterflies fly (the guide
  and the chosen companion among them); the rest settle. Fewer petals fall.
  The setting is the optional `calmMotion` field: older gardens and backups
  read as full motion.
- **P2 / R3** CSS reduced by proof, not by guesswork. A computed-style differ
  compared every property of every element across 34 states (8 views × 2
  themes × phone and desktop, plus onboarding). It found **zero** differences
  after these removals:
  - 79 rules that need a class nothing in the source produces (an old
    CSS-drawn butterfly, a retired shop layout);
  - 245 declarations that a later, identical selector always overrides.

  The built stylesheet went from 112.8 kB to 92.2 kB (−18%).
- **Not done, with reasons.**
  - *Cascade layers*: putting the three sheets in `@layer` in their current
    order changed 1,953 computed values. Inside layers, layer order beats
    specificity, so high-specificity rules in `App.css` lost to plain ones in
    later sheets. Layers would need each conflict decided by hand: a redesign,
    not a consolidation.
  - *Per-view CSS*: only 56 of 294 view-only rules (4.5 kB) could move
    without risking a cascade change where screenshots don't reach.
  - So the 40% target is not met. The safe 18% is.
- **Found and fixed**: the build tool dropped the unprefixed `backdrop-filter`
  wherever a hand-written `-webkit-` line followed it. So the theme's glass
  (header, onboarding card, dock) and the reduce-transparency preference never
  applied in Chrome or the Android WebView. Only Safari saw them.
- **A5** The mobile dock is now solid (`--dock-fill`) with no backdrop blur.
  Even 4% see-through left page text legible behind its labels.

### PR B2 — a lighter Today (b.11 "Next", part 1)

The first half of the "Next" row: the daily page on a phone gets shorter and
asks less. The journal items of the same row (J2, J3, J6) follow in B3.

- **T4 Compact goal rows.** Each goal is one row: a large check target, its
  title and schedule, and a ⋯ menu with Skip today, Snooze…, Edit and
  Archive. On a touch screen, swiping right completes and swiping left
  skips. The direction is decided after a few pixels, so scrolling past a
  row never completes it, and the click that ends a swipe is swallowed, so
  a swipe that ends on a button does not also press it. A mouse, pen or
  keyboard keeps the buttons, which do the same things.
- **T6 Edit a goal properly.** The editor changes the schedule, the days and
  a one-time goal's planned date, not only the title. "Selected days" with
  none ticked is refused, here and in the add form, since such a goal would
  never come round. A goal completed on an earlier day cannot become a
  one-time goal, which would retire it the moment it was saved. Snooze
  offers tomorrow, three days, next week, or a chosen date. The editor takes
  focus when it opens.
- **T7 Gentle day.** One switch on Today, also offered after a heavy-weather
  check-in, shows the day's first three goals, hides the counts and the
  Sunlight number ("Rest counts too"), and points to the companions' free
  care. The three are chosen when the day turns gentle and stay put as they
  are done, snoozed or set aside: finishing one is not a cue for another to
  appear. They, and "show the others" once asked, are kept as drafts for the
  day, so leaving Today does not change them. It is stored as the day it applies to
  (`Profile.gentleDay`), so it ends by itself at midnight without anything
  having to turn it off.
- **T9 Reflection prompts v2.** Sixty prompts in families (savouring,
  gratitude, self-compassion, concrete processing, nature, rest), with no
  "why do I always…" prompts and no trait affirmations. *Another prompt*
  steps through the rotation; *Write freely* drops the prompt. The chosen
  prompt is a draft beside the words, so after a reload a reflection is
  still kept under the prompt it answered. A reflection already written
  today reopens on its own prompt.
- **T11 Next Sunlight tends…** Under the Sunlight meter, a select names the
  plant the next Sunlight grows and lets the gardener choose it
  (`Profile.tendFirstPlantId`). A chosen plant that finishes growing, or is
  removed, falls back to the first plant still growing.
- **M1 Up to three notes for tomorrow.** The recap's last question takes up
  to three short notes, each with its own *Add to tomorrow's goals*. They
  are one draft, a line each, so they survive a reload together. The recap
  stores them a line each in the existing `forTomorrow` field, and the goals
  they became in `plannedGoalIds`, so an older build still shows the notes.
  A draft left by the previous build's single text box keeps every word:
  lines past the third join the third note. The journal edits all three.
  - Left as is: a recap written before this change, whose one note had line
    breaks in it, now shows those lines as separate notes. Every word is
    still there, in order; telling the two apart would need a marker on
    every new recap for a rare, harmless difference.
- **M4 "My evening starts at…".** Settings → Your rhythm moves the hour the
  recap opens (noon to 11pm) and the hour a late night stops offering the
  day before (midnight to 10am). The two ranges cannot meet. Today, the
  Guide and the recap window all read the gardener's hours
  (`Profile.recapOpensHour`, `Profile.recapGraceEndsHour`, both optional).
  - Not done: moving Sunlight's and goals' day boundary to the same hour.
    Every completion, check-in and Sunlight row is keyed by its calendar
    date. Moving the boundary would re-date what is already stored, change
    what a backup means, and shift every streak and rhythm count. That
    needs a migration and its own review, so it is left for a later PR
    rather than slipped in here.
- **Month planner on phones.** It starts folded on a phone-sized screen. A
  chosen day lists its one-time goals; routines, which come round anyway,
  are summed up in a line and listed only when asked.
- Nothing stored changes shape. Every new profile field is optional, and
  `validateGarden` drops a hand-edited value of the wrong type or range.
- **Review.** Eight agents wrote tests for the new code, and three reviewers
  read the change for correctness, accessibility, and security and
  performance. What they found, and what changed:
  - `validateGarden` rebuilt recaps field by field and dropped
    `plannedGoalIds` on every load. It keeps them now, tested by a round trip.
  - The open ⋯ menu was drawn under the rows below it whenever its row was
    hovered or skipped, so its items could not be pressed. The row (and its
    card) with an open menu is lifted, and a skipped row fades its parts,
    not itself. An e2e test now opens the menu, runs axe on it, and presses
    its items.
  - Saving the editor wrote back the goal as it was when Edit was pressed,
    undoing a skip, snooze or archive made from the row meanwhile. It now
    saves only what it edits, and closes if the goal is archived.
  - Focus no longer drops to the page body when a control removes itself:
    the menu returns focus to its button, the editor to its row, an archive
    or snooze to the Goals heading, "Add another" to the new note, "Show the
    other goals" to the first goal it revealed. "Write freely" stays, as a
    pressed toggle, and the month planner's fold is one button.
  - Picking a snooze date no longer acts on each change (the arrow keys step
    through dates nobody chose); it waits for "Snooze until…". Date fields
    stop at the year 9999 and refuse anything that is not a real date.
  - An overdue planned goal can be edited without the browser refusing its
    past date; a goal done today cannot be planned for a later day, which
    would retire it unseen.
  - A quick swipe is measured where the finger lifts. Only the click that
    ends a swipe is swallowed, so a key press or voice command after one
    goes through. The row follows a finger without easing, and reduced
    motion (the setting or the system's) stops its animation.
  - Android's back gesture closes an open goal menu or the editor before it
    leaves Today, as Escape does on the web.
  - The check button's name starts with its visible word ("Care for…"),
    for voice control. Its target, and the new text buttons', are 44 px.
  - A planned note's goal is cut to a goal title's 120 characters, and the
    note itself is kept whole; choosing an unknown or fully grown plant
    changes nothing; the Guide and the hour formatter no longer rebuild on
    every render.
  - A second review of the fixes found more, all fixed: archiving a goal
    open in the editor closes the editor for good; a snooze from the row
    while the editor is open keeps its new date; turning "Write freely" off
    returns to the prompt that was showing; the goal menu closes when focus
    tabs past it; Edit chosen again refocuses the editor; the swipe rows
    still let two fingers zoom; the recap's toggle keeps one name, with
    pressed shown by its state and a tick; the Guide follows the chosen
    plant and says nothing of a late night that ends at midnight.
- Tests: 895 unit and 54 e2e pass; coverage is 91.3% of lines and 85.2% of
  branches.

### PR B3 — the journal gives back (b.11 "Next", part 2)

The journal items of the "Next" row. A journal kept for a year was a
timeline paged thirty days at a time; now it can be searched, seen at a
glance, and taken away to read.

- **J2 Find things.** A search above the timeline matches every word typed,
  forgiving case and accents ("rio" finds "río"), across check-in notes,
  reflections and recaps. Toggles keep only check-ins, reflections or
  recaps, and a select keeps one weather; a "Not sure" day matches only
  "Not sure", never the middle weather it is stored as. The text is
  normalised once per change to the entries and the filter is deferred, so
  typing stays quick in a long journal. Nothing leaves the device.
- **J3 Weather calendar.** A month grid, and a year in pixels, coloured by
  each day's weather on a light-to-dark ramp with a key, so colour is never
  the only sign. A day with an entry is a button named with its date and
  weather; choosing it shows that day in the timeline, beyond the first
  page if need be, and gives it focus. The calendar never goes past this
  month or before the first check-in, and it says nothing it would have to
  count or average: no scores, no trends.
- **J6 Readable copies.** "Take your words with you" saves the journal as
  Markdown or as a printable page, and the check-ins as a spreadsheet, on
  the phone's own save screen in the Android app. The JSON backup is
  unchanged.
  - The printable page escapes every piece of the gardener's text and
    carries its own policy (`default-src 'none'`), so nothing in it can run
    or load even if escaping were ever wrong.
  - In Markdown, journal text cannot start a heading, list, quote, code
    block, table or raw HTML.
  - The spreadsheet quotes every field, starts with a byte-order mark so
    accents survive, and puts an apostrophe before anything that a
    spreadsheet would read as a formula.
  - The code that builds the files is loaded only when one is asked for.
  - A file is named by the gardener's own calendar day, the day written
    inside it; backups and the other saved files too, which used to take
    the date in UTC.
- **Review.** Three builders wrote the parts in parallel, and three
  reviewers tried to break them (security, correctness and performance,
  accessibility). Fixed from what they found:
  - In the spreadsheet, a later line of a note, or what follows a tab or a
    semicolon, could still run as a formula in a spreadsheet set to split
    on those, as much of Europe is; LibreOffice did. Every such start in a
    field is guarded now.
  - In Markdown, `$`, `^`, `@`, `<` and `>` are escaped with a backslash,
    and a line starting "a)", "(1)" or "iv." no longer becomes a pandoc
    list, so money, smileys and mentions read as typed.
  - Opening a day already on the first page did nothing, and then took
    focus out of the search on the next keystroke. Each choice is now its
    own request, answered at once.
  - Search folded only Latin accents correctly: it now decomposes before
    lower-casing (so "𝐇𝐞𝐥𝐥𝐨" and "Straße" are found), and keeps the marks
    that are part of a letter in Devanagari or Japanese, which it used to
    strip, finding "school" for "cuckoo".
  - The match count waits for the deferred search, so a count for the
    whole journal is never read out in passing; the search stays, with
    focus in it, when cleared on an empty journal.
  - The calendar reaches a reflection kept before the first check-in, and
    a year in pixels is no longer hundreds of tab stops: each month's name
    is the keyboard's way in.
